OpenAI 发布《How OpenAI’s Performance Factory keeps ChatGPT fast》，作者为技术团队成员 Okay Zed 与 Cyrus Forbes。文章页只标出日历日期 November 19, 2026，没有时刻；计时以 openai.com 新闻 RSS 中该文的 pubDate 为准，为 Thu, 19 Nov 2026 08:00:00 GMT。该文把 Performance Factory 写成在云端运行的系统，用 Codex 及其模型寻找并修复性能问题。工程师为重复性工作定义工作流，并为执行这些工作的 Codex 智能体写说明。其中的回归工作流（Regression Workflow）在性能警报触发时打开任务。智能体调查变慢的原因，把发现记在任务里，并提出修复，交由工程师复核。部署之后，另一个智能体接上同一任务，检查性能是否回到基线。该文写明，从调查、撰写修复到验证缓解，这条工作流把修复回归的过程自动化了。在三个多月里，回归工作流跟踪了 1,700 次以上的调查，并为 600 个以上的案例找到根因。该文把这写成每天 17 次自动调查。系统分成四部分：带可配置工作流的任务服务、把就绪工作分给智能体的调度循环、在云端运行 Codex 回合的内部 API，以及在情况变化时唤醒智能体的订阅，例子包括 GitHub 复核评论发布或部署完成。云端的 Codex 回合跑在其网络内部的环境里，可以访问代码仓库，以及工程师使用的指标、日志、追踪、CPU 剖面和内存快照。智能体以服务身份运行，因此可以限定权限，并看出哪些动作来自这些性能智能体。该文写明早期的智能体有时停在第一个说得通的解释上，其中有些诊断后来证明是错的，于是加入对抗式复核：另一次 Codex 会话尝试推翻所提出的诊断。文中的一个例子是，智能体把失败的 ChatGPT 对话追溯到图像下载错误，并标成已经找到原因；复核者注意到负责定位文件的内部服务已经恢复，而图像请求仍在失败，于是重新打开调查。该文另写明，在对 100 条根因建议所做的人工复核里，他们把 70% 评为准确，30% 需要进一步细化，或没有完全建立因果关系。回归工作流用不同的回合分别调查、质疑诊断和提出修复，该文说这是为了靠制衡提高准确程度；该文没有给工作流本身另报一个准确率。诊断通过复核后，工作流让 Codex 实现修复并打开拉取请求，由工程师决定是否合并。该文写明把修复做对比找到原因更难，见过提案比所需更复杂，或引入新问题的情况；有些修复还需要更高层的架构决定，例如加缓存可能提高性能，但也会引入过期数据。部署后，智能体检查是否回到早先的基线：回到了就标为已解决；只部分恢复就结束原来的回归，并为剩下的变慢另开任务；没有改善就把回归送回调查。该文说他们正在用智能体提案和工程师最终合并的改动做对照，建立评估与改进循环，也在探索用合成性能测试让智能体在请人复核前先测量并修改提案，并探索让智能体借助其他智能体复核工具识别低风险改动，最终在没有人在环的情况下交付这些修复。该文写明，今天的瓶颈可能是等待工程师复核并合并修复。上述次数和 70% 的复核比例都是 OpenAI 给出的，本刊未复跑。RSS pubDate 为 Thu, 19 Nov 2026 08:00:00 GMT。

OpenAI published How OpenAI’s Performance Factory keeps ChatGPT fast, by Okay Zed and Cyrus Forbes, Members of Technical Staff. The article page shows only the calendar date November 19, 2026, with no time of day. This item times it by the pubDate on its openai.com news-RSS entry, Thu, 19 Nov 2026 08:00:00 GMT. The post describes the Performance Factory as a system that runs in the cloud and uses Codex and OpenAI's models to find and fix performance problems. Engineers define workflows for recurring jobs and write instructions for the Codex agents that carry them out. Its Regression Workflow opens a task when a performance alert fires. An agent investigates the slowdown, records findings on the task, and proposes a fix for an engineer to review. After deployment, another agent picks up the same task to check whether performance has returned to baseline. The post says that from investigating, to authoring the fix, to verifying mitigation, this workflow has automated the process of fixing regressions. In just over three months, the Regression Workflow tracked more than 1,700 investigations and root-caused over 600 cases. The post states that as 17 automated investigations every day. The system has four parts: a task service with configurable workflows, a dispatch loop that assigns ready work to agents, an internal API that runs a Codex turn in the cloud, and subscriptions that wake agents when something changes, with examples that include a GitHub review comment posting or a deployment completing. The cloud Codex turn runs on an environment inside OpenAI's network, with access to code repositories and to the observability tools engineers use, such as metrics, logs, traces, CPU profiles and memory snapshots. The agent runs under a service identity, so permissions can be scoped and actions from these performance agents can be distinguished. The post says that early on, agents sometimes stopped at the first plausible explanation and some of those diagnoses turned out to be wrong, so it added an adversarial review: a separate Codex session that tries to disprove the proposed diagnosis. In one example in the post, an agent traced failing ChatGPT conversations to image-download errors and marked the cause as found; the reviewer noticed that the internal service responsible for locating files had already recovered while image requests were still failing, and reopened the investigation. The post separately says that in a manual review of 100 root-cause suggestions, they graded 70% as accurate, with 30% needing further refinement or not fully establishing causality. In the Regression Workflow, different turns investigate regressions, challenge diagnoses and propose fixes. The post says that is to increase accuracy through checks and balances. It does not give a separate accuracy figure for the workflow itself. After a diagnosis passes review, the workflow asks Codex to implement a fix and open a pull request, and an engineer decides whether to merge it. The post says getting fixes right has been harder than finding the cause. It says there have been cases where the proposed changes are more complicated than necessary or introduce new issues, and that some fixes need a higher-level architectural decision, such as adding a cache that might improve performance but introduce stale data. After deployment, an agent checks whether performance has returned to its earlier baseline. If it has, the agent marks the task resolved. If recovery is only partial, the agent resolves the original regression and opens a new task for the remaining slowdown. If there is no improvement, it sends the regression back for investigation. The post says they are building an evaluation and improvement loop by comparing the fixes agents propose with the changes engineers ultimately merge. It also says they are exploring synthetic performance tests so agents can measure and revise a proposal before asking an engineer for review, and exploring whether agents could use other agentic review tools to identify low-risk changes and eventually ship those fixes without a human in the loop. The post says that today the bottleneck may be waiting for an engineer to review and merge the fix. These counts and the 70% review rate are OpenAI's. TUJL has not rerun them. That page's article:published_time is the calendar date 2026-11-19 with no time of day, so this item does not time the post by it. A meta tag named published_time on the same page matches the JSON-LD datePublished. The post says Tool Retrieval is available in preview in the Interactions API. When an agent connects to dozens or hundreds of tools, sending every parameter schema on every request increases input tokens, adds latency, and lowers tool-selection accuracy as the candidate list grows. Tool Retrieval keeps the tool library on standby and loads parameter schemas only when the current task needs them. To turn it on, add a tool_search tool to the request and set defer_loading to true on the tools to hold back. The model still sees the name and description of every deferred tool, while the parameter schemas stay out of context. When the model asks for a tool by name, the API loads the full schema and the model calls the function. The post says those three steps happen inside the same request. It says they appear in interaction.steps, with types tool_search_call, tool_search_result and function_call. There is no index to build or host. Gemini runs the search on the server. Frequently used tools can stay loaded up front, and the long tail can be deferred. The post says this works with prefix caching: deferred schemas stay out of the start of the prompt, and schemas the model loads are added later in the conversation, so the cached prefix stays the same from turn to turn. Remote MCP servers work too. Setting defer_loading to true on an mcp_server tool loads every tool that server exposes on demand, without listing them one by one. If the caller keeps its own tool registry, embedding index or per-user permission filter, it can set the tool_search execution to client and define the search parameters. Client-side retrieval adds one round trip per search, because the app runs the lookup. Tools do not need to be declared up front, so a new tool can be exposed mid-conversation when a user connects an integration. On price, the post says there is no separate charge. Input and output tokens are billed at the standard rates for the model called. Turning on tool_search adds a small, fixed block of input tokens. The post does not state the size of that block. Each schema the model loads is billed as input for the rest of the conversation, the same as a tool declared up front. The post says tokens are saved when the schemas that are never loaded outweigh the ones that are, says that is the usual case for large libraries, and says to measure it against one's own traffic. On availability, the post says Tool Retrieval works with Gemini 3.6 and later models, including all Gemini 4 models, in the Interactions API. The code sample in the post calls gemini-4-hydrogen and marks a refund function as deferred. That sample is an illustration in the announcement, not a result TUJL reran.
